## Successes & Strengths

1. **Zéro surprise de scope** — Contrairement à Epic 1, aucune exigence non identifiée n'a émergé en cours d'implémentation. Les ACs étaient assez précis pour couvrir tous les cas réels. Le switch web → desktop était connu et traité comme une décision délibérée, pas un incident.

2. **Story 2-1-desktop : cleanup chirurgical** — Tout le code web-only (OPFS, handle-store, permission re-grant, `pendingPermissionHandle`, `WEB_NATIVE_PATH`) éliminé en une story bien scoped. 13 ACs, tous verts, aucune régression. Le state machine `VaultSetupPage` simplifié de 4 à 3 états.

3. **La review AI a rattrapé les violations d'architecture** — 4 HIGHs dans 2-2 (boundary violations, chemin hardcodé, zéro test sur l'import Android) tous détectés avant merge et corrigés. L'extraction du `vault-db` adapter dans `shared/platform/` a produit un vrai adapter avec DI et 8 tests unitaires.

4. **Qualité maintenue story par story** — 179 → ~215 tests, quality gates propres à chaque commit. Aucune story n'a mergé avec des tests cassés.

---

## Challenges & Growth Areas

1. **Violations d'architecture arrivant à la review** — Story 2-2 avait des appels Capacitor dans `shared/db/` et un chemin Android hardcodé, malgré une spécification qui prescrivait l'extraction vers un adapter. Le problème n'est pas la lecture d'AGENTS.md (il est en contexte automatiquement) mais l'absence de vérification active des règles avant d'écrire du code — notamment sur des implémentations complexes comme l'import binaire Android.

2. **Documentation drift persistant** — Le H1 de 2-3 était corrigé dans le code mais la checkbox restait `[ ]` dans le story file. Pattern récurrent depuis Epic 1. La story 2-3 affichait `Status: in-progress` alors que sprint-status la marquait `done`.

3. **Consommation de tokens** — Une US par session de quota reste difficile. Sources identifiées : lectures redondantes d'AGENTS.md dans les skills custom, dev notes embarquant des snippets complets de code plutôt que des références aux fichiers existants, fichiers de planning lus en entier plutôt que ciblés par Grep.

---

## Key Insights & Lessons Learned

1. **La boundary enforcement ne doit pas dépendre du comportement de l'agent** — Un hook post-edit mécanique qui détecte les violations est plus fiable qu'une instruction comportementale, même si le fichier de règles est en contexte.

2. **Les dev notes doivent expliquer les décisions et les pièges, pas réimplémenter le code** — Un snippet de 5 lignes illustrant le pattern suffit. Copier une implémentation complète qui sera de toute façon dans les sources coûte des tokens sans valeur ajoutée.

3. **La checklist de review doit être réconciliée dans le même commit que le fix** — Pas de "je cocherai après". Si le fix est dans le commit, la checkbox l'est aussi.
