## Successes & Strengths

1. **5/5 stories livrées, zéro incident** — epic complété sur une fondation desktop entièrement nouvelle.

2. **La platform adapter pattern d'Epic 1 a tenu** — ajouter le support desktop s'est limité à créer quatre fichiers `*.desktop.ts` et à mettre à jour les sélecteurs `index.ts`. Pas de refactoring de code feature.

3. **Stories planifiées avec une précision exemplaire** — les dev notes prescriptives (pattern `isTauri()`, guards Vite `define`, risques de circular import, chemins Tauri SQL) ont éliminé des catégories entières d'erreurs avant l'implémentation.

4. **La sécurité a été traitée comme une story à part entière** — SonarQube a flagué le hardcoded credential dans 8.3. Au lieu d'un patch inline, une story dédiée (8.4) a produit une vraie solution : OS keychain via `keyring`, Tauri command, guard compile-time contre le mock en release. C'est le bon process.

5. **La revue de code AI a rattrapé une erreur de protocole critique** — l'approche initiale CDP pour le E2E desktop (`chromium.connectOverCDP`) était techniquement incorrecte : CDP et WebDriver sont deux protocoles distincts. Détecté en revue, corrigé vers WebDriverIO avant merge.

6. **Test suite en forte croissance** — 73 → 179 tests sans forçage, par accumulation organique story par story.

## Challenges & Growth Areas

1. **La suppression de la cible web est un changement de contrat, pas juste de code** — retirer `createWebDb()` a modifié la sémantique de `initDb()` : résultat `null` désormais possible là où c'était toujours non-null. Tous les appelants en aval ont dû être audités manuellement. Ce type de changement doit être signalé explicitement dans le PR body.

2. **Les adapters desktop ne sont pas couverts par les tests unitaires — et c'est structurel** — les appels IPC vers le backend Rust (filesystem, file-picker, secure-storage, preferences) ne peuvent pas s'exécuter dans JSDOM. Le seul filet de validation est `npm run tauri:dev` en local. C'est une contrainte durable de l'architecture Tauri, à documenter explicitement plutôt qu'à traiter comme de la dette.

3. **Le E2E desktop en CI n'a jamais été vérifié de bout en bout** — Task 5 de story 8.5 est marquée done sur la base d'une validation `yaml.safe_load`. Que `tauri-driver` démarre correctement, que le binaire Tauri se lance sous `xvfb-run`, que WebDriverIO se connecte et que le test passe : non prouvé. La décision est prise de retirer ce step de la CI (Option A).

4. **La documentation dérive dès qu'une implémentation s'éloigne du plan** — deux occurrences sur Epic 8 : l'approche E2E (CDP → WebDriverIO non documenté dans le story file final), et le sélecteur d'adapter entre 8.2 et 8.3 (décalage temporaire entre code et doc). Pattern récurrent depuis Epic 1, adressé structurellement en AI-3.

5. **La bascule web + Android → desktop + Android a été délicate** — la gestion de la cible web comme cible morte (code conservé mais non sélectionné) a introduit de la confusion sur plusieurs stories. La transition est désormais complète, mais a demandé une attention constante pour éviter les régressions silencieuses.

## Key Insights & Lessons Learned

1. **Un changement de contrat de fonction publique mérite une mention explicite dans le PR** — "ce changement modifie la sémantique de `initDb()` pour tous les appelants" est exactement ce qu'un reviewer a besoin de voir. Ne pas le laisser implicite dans le story file.

2. **La sécurité détectée en cours d'epic doit spawner une story dédiée** — le pattern Epic 8 (SonarQube → story 8.4 → vraie solution) est le bon réflexe. À répliquer sur tous les findings SonarQube futurs.

3. **Le E2E desktop en CI est prématuré tant que les parcours testables sont minimalistes** — le compile check Tauri est le bon niveau de filet automatisé à ce stade. Le E2E desktop reviendra sur la table quand Epic 2 aura produit des flux utilisateur réels à valider.

4. **La documentation est un livrable de la story, pas une tâche post-merge** — README, `AGENTS.md`, `architecture.md`, ou document dédié : tout document affecté par une story sort dans la même PR que le code. Si aucun document existant ne couvre le sujet, le créer.

5. **Les contraintes d'architecture non testables automatiquement doivent être documentées explicitement** — "les adapters desktop ne sont validables qu'en local via `npm run tauri:dev`" est un fait architectural à documenter, pas une dette à rembourser.
