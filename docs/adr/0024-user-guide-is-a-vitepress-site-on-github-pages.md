# The user guide is a VitePress site on GitHub Pages

Lekto documents itself for agents and developers — `CONTEXT.md`, the ADRs, and the
build and test docs — but a person who installs the app has nowhere to learn it. We
need an end-user guide at a web address a user can reach, describing the product as it
is and staying in step with it (spec #96).

We decided to publish that guide as a static site generated by **VitePress**, pinned to
the stable 1.6.x line (2.0 is alpha), and hosted on **GitHub Pages**. The guide's
content lives in a dedicated root of this repository that is **never** under `docs/`, so
the internal material — ADRs, research, the build and test docs — can never be published
by accident. It is deployed by a GitHub Actions workflow that follows GitHub's artifact
pipeline (`configure-pages`, `upload-pages-artifact`, `deploy-pages`) rather than a
`gh-pages` branch: it builds on every pull request as a **required** check, and
redeploys only `latest`, filtered by path, when a merge touches it. There is **no
versioned documentation** — one site, always current.

The guide is also a **documented surface**: the `/sync-docs` step of `/deliver` updates
the affected page in the same pull request as the feature that changed it, as it already
reconciles `CONTEXT.md`, the ADRs and the build and test docs. What makes that reliable
is a feature→page map kept with the guide, so a change names the page it touches instead
of an agent guessing. Because the project's licence gate (`checkDependencyLicences`,
ADR-0011) sees only Gradle dependencies, the docs workflow runs its own npm licence
check, so "every dependency is AGPL-compatible" keeps holding across tooling the Gradle
gate cannot reach.

We rejected **MkDocs with Material for MkDocs** — the ecosystem's default reach — because
MkDocs' last release predates this decision and Material is in maintenance behind an
incomplete successor, a supply-chain risk for a site we expect to sit untouched for long
stretches. We rejected **mdBook**: it has the smallest dependency surface, but the guide
must eventually be bilingual (French) and mdBook's i18n is an external,
officially-unsupported helper rather than a built-in. We rejected **Docusaurus**, whose
unique advantage is first-class versioning, as the heaviest of the three and the only one
whose first-class search is a hosted service. VitePress is the middle choice we want: a
light Node toolchain, built-in **local** search (no hosted index, no user queries leaving
the page — consistent with ADR-0002's local-first posture), and first-class i18n ready for
the French tree.

We deferred versioning deliberately. Nothing is released yet, and both clients update
themselves, so a user reads the latest build and `latest` is the only version they need.
The **Vault**'s own format version (ADR-0014) is not a counter-argument: it is a
compatibility gate the app enforces — a format bump is migrated in-app, and sync
conflicts are resolved in the merge (ADR-0015) — not a procedure a user follows from a
page, so data versioning does not create a need for documentation versioning. Versioned
docs return to the table only if Lekto ever maintains several release lines at once.

**Consequences**: the published site is **documentation**, not the web client ADR-0008
closes — it introduces no browser target for the app. Only the generated site is
published; the internal `docs/` tree is never a source root. Reviewing a change now
includes the guide: a feature pull request is not done until the page that describes it
matches. See `docs/research/user-docs-on-github-pages.md` for the tool and deployment
comparison behind this decision.
